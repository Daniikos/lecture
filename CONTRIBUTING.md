# Как вносить правки

Репозиторием управляет один человек (мейнтейнер). Все изменения в `main`
проходят через pull request; напрямую в `main` не пушит никто, включая
мейнтейнера.

## Какие правки бывают

| Тип | Что это | Как оформлять |
|-----|---------|---------------|
| Ошибка распознавания | опечатка, потерянный символ, неверно распознанная формула, не то, что в рукописи | PR сразу, без обсуждения |
| Вёрстка | формула не так набрана, рисунок съехал, таблица разваливается | PR сразу |
| Новая лекция | распознанный и набранный файл новой лекции | PR; файл должен собираться |
| Реструктуризация | переименование, разбиение файлов, вынос преамбулы, переход на новые окружения | сначала Issue, PR только после согласования |
| Ошибка в математике | утверждение в лекции неверно или неточно | Issue, не PR |

Последнее — принципиально. Опечатка — вопрос сверки с рукописью, её
можно мержить за минуту. Верна ли теорема — вопрос обсуждения, и он не
должен блокировать мерж опечаток в том же файле.

## Процесс

1. Участники с правом записи создают ветку в репозитории, остальные — форк.
   Имя ветки: `fix/matan-2026-09-02`, `add/matan-2026-09-09`,
   `restructure/preamble` — тип и что трогаем.
2. Один PR — одна лекция и одна тема правки. PR «исправил опечатки в трёх
   лекциях и заодно переделал рисунок» ревьюить дольше, чем три отдельных.
3. Сборка в PR должна быть зелёной. Если она упала — смотрите лог
   в Actions, там `file:line:error`.
4. Мейнтейнер ревьюит и мержит. Если PR висит без ответа больше недели —
   напомните в комментарии, это нормально.

Сообщение коммита: `<курс> <дата>: что сделано`, например
`matan 2026-09-02: исправлены опечатки в разделе «Операции над множествами»`.

## Правила для файлов

- Имя файла — дата лекции в формате ISO: `2026-09-02.tex`. Не `02_09`,
  не `лекция3`: ISO-даты сортируются хронологически сами.
- Кодировка UTF-8, переводы строк LF. Это принудительно задано в
  `.gitattributes` и `.editorconfig`; если ваш редактор их не читает,
  проследите вручную. PR, в котором diff показывает «изменён весь файл»
  из-за CRLF, будет возвращён.
- Каждый `.tex` собирается самостоятельно командой
  `latexmk -pdf <файл>`. Никаких зависимостей от файлов вне репозитория.
- Отступ — два пробела, табуляций нет.
- Не переформатируйте текст, который не меняете по смыслу: не
  переносите строки, не меняете пробелы, не «причёсываете» соседние
  абзацы. Такие правки раздувают diff и прячут содержательные изменения.
  Форматирование — отдельным PR с пометкой «только форматирование».

## Соглашения по разметке

Так размечены существующие лекции. Придерживайтесь их, пока не принято
другое (см. «Что дальше»).

- Разделы — `\section*{...}` и `\subsection*{...}`, без нумерации:
  нумерация тем в рукописи не совпадает с нумерацией по лекциям.
- Определяемый термин — `\textbf{...}` внутри фразы
  («Множество называется \textbf{конечным}, если...»).
  Подчёркивание `\underline{...}` — только там, где оно есть в рукописи.
- Примеры — `\textbf{Пример N (способ).}` в начале абзаца.
- Ключевые формулы, обведённые в рукописи, — `\boxed{...}`.
- Диаграммы Эйлера–Венна — макросом `\venn{<заливка>}{<подпись>}`
  из преамбулы; новые рисунки — TikZ, не растровые картинки.
- Расхождение набора с рукописью фиксируется комментарием
  `% в оригинале ...` прямо у места расхождения. Молча «исправлять»
  рукопись нельзя: это уже вопрос для Issue.
- Русские кавычки — `<<...>>`, тире — `---`.

## Что не коммитить

`.gitignore` это уже закрывает, но проверьте перед PR:

- мусор сборки: `*.aux`, `*.log`, `*.fdb_latexmk`, `*.fls`, `*.synctex.gz`,
  `*.dvi`, папка `build/`;
- сами PDF — их собирает CI;
- файлы IDE: `.vs/` (Visual Studio), личные настройки `.vscode/`
  кроме `settings.json` и `extensions.json`, `.idea/`, `.obsidian/`;
- сканы рукописи. Они нужны для сверки, но бинарники раздуют
  репозиторий — храните их отдельно (Release assets или общая папка).

## Как писать Issue об ошибке в математике

Заголовок: `matan 2026-09-02: <кратко, что не так>`. В тексте:

1. файл и место — раздел, формула или номер примера;
2. что написано;
3. что, по-вашему, должно быть, и почему (ссылка на источник, если есть);
4. есть ли это в рукописи или появилось при наборе.

## Что дальше

Решения, которые отложены сознательно и требуют отдельного обсуждения
(Issue с пометкой `restructure`):

- **Общая преамбула.** Сейчас каждый файл несёт полную преамбулу. Когда
  лекций станет больше десятка, вынести её в `matan/preamble.tex` и
  подключать через `\input`; CI при этом надо будет научить не собирать
  `preamble.tex` как отдельный документ.
- **Семантические окружения.** `\textbf{конечным}` — это оформление, а не
  структура: определения нельзя ни пронумеровать, ни собрать в указатель,
  ни найти иначе как глазами. Переход на `amsthm`
  (`definition`, `theorem`, `example`, `remark` с метками `def:`, `thm:`,
  `ex:`) — один PR на все файлы сразу, чтобы не жить в двух конвенциях.
- **Маркеры в рукописи.** Если при письме ставить фиксированные пометки
  («Опр.», «Т.», «Д-во», «Пр.», «Зам.», ∎), расстановка окружений после
  распознавания делается скриптом, а не руками.
- **Одно предложение — одна строка.** Для новых файлов имеет смысл
  перейти на этот формат: diff становится построчным и читаемым, а два
  PR в один файл перестают конфликтовать. Существующие файлы
  переформатировать одним отдельным PR.
- **Оглавление по темам.** Лекция — единица доставки, тема — единица
  смысла. Когда файлов станет много, над `matan/README.md` появится
  слой «тема → в каких лекциях».
